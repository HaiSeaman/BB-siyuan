## 一、这个插件到底解决什么问题

主人在思源里写日记。写完以后，他想要一份「更像样」的成稿：内容被扩展、被归纳、被总结。

他不想自己一段段改写，也不想学什么「提示词工程」。他只想：

1. 把今天写的内容交给面板
2. 点一下某个提示词（比如「复盘 + 三条建议」）定下规则
3. 在输入框里继续说，AI 每条都按这套规则回答
4. 等 AI 写完，点「复制」，自己粘到思源里保存

中间如果 AI 需要「今天几号」「最近有什么新闻」这类外部信息，它可以自己去查 —— 这就是 MCP 的作用。

**一句话定位**：一个提示词驱动的 AI 生成面板，专为「把草稿变成成稿」设计。

**两条最重要的边界：**

1. **插件只读不写。** 它绝不修改、绝不覆盖、绝不自动插入思源里的任何笔记。生成的成稿只出现在插件面板里，由你点复制、自己粘贴保存。
2. **不碰"选中笔记内容"这条通道（1.1.0 起）。** 要处理的内容由你直接敲进输入框。插件不去读你的选区。

## 二、要什么，不要什么

### 要（必需）

| # | 需求 | 说明 |
|---|---|---|
| 1 | 自定义 API 地址与模型 | 任意 OpenAI 兼容中转站 + 官方 Anthropic / Gemini 原生协议 |
| 2 | 思考开关与强度 | 能开、能关、能调档；调用方按模型家族自动翻译成正确的参数 |
| 3 | MCP（仅外网查询，手动添加） | 真实的 MCP 协议客户端。服务器地址/命令由主人自己粘贴，插件不预置清单 |
| 4 | 自定义提示词模板 | 插件的心脏。模板里能插入选中内容、日期、时间、文档标题 |
| 5 | 主流 AI 对话能力 | 流式打字机、多轮上下文、Markdown 渲染、停止、重生成、**一键复制** |

### 不要（明确排除）

- **不写入思源笔记**：不改、不覆盖、不自动插入。只给复制按钮，主人自己粘贴
- **不注入"选中的笔记内容"**（1.1.0 追加）：内容直接敲进输入框，插件不读选区
- 不做笔记内部检索 / RAG / 向量库 / 知识库问答
- 不做多模型并排对比
- 不做翻译、起标题、划词解释等零散小工具
- 不做记忆系统、技能系统、定时任务
- 不做内置 MCP 服务器清单，不做 API Key 托管
- 不做移动端专门适配（桌面能用就行，移动端不保证）
- 不做中英双语、不做集市上架材料（只自己用）

**为什么这么砍**：主人的原话是「不需要加入过多的辅助功能」「我都是用提示词来自定义我的内容模板的」「不要牵扯到原本思源日记里面的东西」。功能越少，代码越稳，出问题越好查。

**「只读不写」带来的好处**：整个插件不需要任何「写块 / 更新块 / 插入块」的思源 API，误操作毁掉日记的可能性为零。这是本方案最省心的一条设计。

## 三、五件事各自怎么做

### 3.1 自定义 API 地址与模型

**数据结构**（存在插件自己的数据文件里，不进思源内核 AI 设置）：

```
供应商 Provider
├── id            内部唯一标识
├── name          显示名（比如「某中转站」）
├── baseURL       接口地址，如 https://api.xxx.com/v1
├── apiKey        密钥
├── protocol      协议类型：openai | anthropic | gemini
├── headers       额外请求头（可选，键值对列表）
└── timeout       超时秒数

模型 Model
├── id            模型名，如 gpt-4o、claude-sonnet-4
├── providerId    属于哪个供应商
├── displayName   显示名
├── maxTokens     最大输出
├── temperature   温度
├── thinkingCapable  该模型是否支持思考
└── contextMessages  带多少条历史
```

**三种协议各管什么**：

- `openai`：`POST {baseURL}/chat/completions`，标准 OpenAI 格式。**覆盖 95% 的第三方中转站**，这是主力。
- `anthropic`：`POST {baseURL}/v1/messages`，Claude 官方格式。Claude 原生思考参数只在这里生效。
- `gemini`：`POST {baseURL}/v1beta/models/{model}:streamGenerateContent?alt=sse`。

**为什么分三种而不是一种**：OpenAI 兼容层是事实标准，但 Claude 和 Gemini 的思考参数在兼容层里会被改写或丢弃。要拿到「真正的思考强度」，必须走原生协议。这是主人要「原生」的代价，也是必要的。

**为什么不用思源自带的 AI 设置**：思源 3.8.10 内核确实有 `/api/ai/*`、`/api/agent/*`，自带流式、思考、MCP。但它的请求结构里**没有任何可以替换系统提示词的位置**（`agentChatReq` 只有 `message`、`references`、`editorContext`）。主人的核心需求就是「用我自己的提示词模板」，所以这一层必须自己做。代价是：思源里配过的模型在这个插件里要再配一次，两套配置互不影响。

**风险**：部分第三方中转站也会声称「支持 Claude」，但用的是 OpenAI 格式。所以协议类型让用户自己选，默认 openai。

**模型列表**：填了 baseURL + apiKey 后，可以点「拉取模型」调 `GET {baseURL}/models`。失败就算了，允许手填 —— 很多中转站不开放这个接口。

### 3.2 思考开关与强度

**统一档位**（界面上一排按钮，从弱到强）：

```
关 → 最小 → 低 → 中 → 高 → 最高
none  minimal low  medium high  max
```

**为什么统一**：不同厂商参数名和取值都不一样。用户不该记这些。界面只给一套档位，代码里按模型家族翻译。

**翻译表**（核心逻辑，独立成一个模块）：

| 模型家族 | 开启思考 | 强度参数 |
|---|---|---|
| OpenAI GPT / o 系列 | 不额外传 | `reasoning_effort: low/medium/high` |
| DeepSeek R1 / V4 | `thinking: enabled` 或 `reasoning_effort` | V4 支持 `high/max` |
| Claude（原生协议） | `thinking.budget_tokens` | 按档位算 token 预算（1024 ~ 32768） |
| Claude（4.6+ 新版） | `effort` 字段 | `low/medium/high/max` |
| Gemini 2.5 | `thinkingConfig.thinkingBudget` | 0 / 1024 / 4096 / 16384 / 32768 |
| Gemini 3 | `thinkingConfig.thinkingLevel` | `LOW/MEDIUM/HIGH` |
| Kimi / MiniMax | `thinking: {type:'enabled'}` | 不支持档位，只能开关 |

**关闭思考时的清理**：必须把这些字段全删掉 —— `thinking`、`reasoning_effort`、`enable_thinking`、`reasoning_split`、`extra_body.google.thinking_config`。少删一个，某些 API 就会报 400。

**显示思考过程**：流式响应里如果有 `reasoning_content` 或 `thinking_delta`，单独渲染成一块灰色折叠区，默认收起。用户想看过程就展开。

**风险**：模型名识别靠字符串匹配（比如 `claude`、`gemini`、`deepseek`）。中转站如果改了模型名（如 `my-claude-pro`），可能识别不到，就退化成「只发开关、不发档位」。可接受。

### 3.3 MCP（只查外网，手动添加）

**只做 MCP 客户端（client），不做服务端，不预置任何服务器清单。**

主人自己把服务器的地址或启动命令粘进来。插件负责：连接、握手、发现工具、把工具交给模型、执行调用、把结果回传给模型。

**三种传输方式**：

| 传输 | 用途 | 支持环境 |
|---|---|---|
| Streamable HTTP | 主流，POST + 可选 SSE 流 | 全部（含浏览器/移动端） |
| SSE（旧版） | 兼容老的 MCP 服务器 | 全部 |
| stdio（子进程） | 本地 MCP 服务器，如 `mcp-server-time` | **仅桌面端** |

**为什么 stdio 只在桌面端**：它需要 spawn 一个本地进程。浏览器和手机没有这个能力。

**桌面端怎么拿到进程能力**：思源桌面端是 Electron，插件里可以用 `window.require('child_process')` 和 `window.require('path')`。这是思源官方允许的能力（社区插件 `siyuan-plugin-copilot` 就用它开子进程和网络连接）。

**风险（必须在方案里写明）**：
- 这是 Electron 的「非公开接口」，思源未来版本可能收紧。所以代码要做能力检测：`typeof window.require === 'function'`，拿不到就禁用 stdio 选项并给用户提示。
- stdio 服务器要在用户电脑上装好（比如 `npx -y @modelcontextprotocol/server-time`），插件只负责启动它。

**配置结构**：

```
MCP 服务器
├── id
├── name          显示名
├── type          http | sse | stdio
├── url           http/sse 用
├── headers       http/sse 用（比如 Authorization）
├── command       stdio 用，如 npx
├── args          stdio 用，如 ["-y","@modelcontextprotocol/server-time"]
├── env           stdio 用，环境变量
└── enabled       是否启用
```

**连接与工具发现**：
1. 启动时对每个 `enabled` 的服务器执行 `initialize` 握手
2. 调 `tools/list` 拿到工具清单（名称、描述、参数 schema）
3. 把所有服务器的工具合并成一份清单，传给模型（OpenAI 的 `tools` 字段 / Anthropic 的 `tools` 字段）
4. 模型返回 `tool_calls` 时，路由到对应服务器执行 `tools/call`
5. 结果回灌给模型，继续生成

**工具命名冲突**：多个服务器有同名工具时，前缀服务器名，如 `time__get_current_time`。

**安全**：MCP 工具默认直接执行（因为只做查询）。如果工具描述里检测到明显的写操作（delete/write/update），弹一次确认框。用户可以选择「本次会话始终允许」。

**如果你没有现成的 MCP 服务器**：插件会在 MCP 设置页放一段说明和几个可复制的命令样例（比如 `npx -y @modelcontextprotocol/server-time`），但**不替你装、不替你申请 Key、不预置成默认项**。要不要用、用哪个，由你决定。

**失败处理**：某个服务器连不上，不影响其他服务器；界面显示红点 + 错误原因。

### 3.4 自定义提示词模板（核心）

**模板结构**：

```
模板
├── id
├── name          比如「日记复盘」
└── content       模板正文
```

**模板正文 = 系统提示（system prompt）。** 不设 `mode` 字段。

**为什么**：主人要的是「用我的提示词定义输出模板」。提示词就是告诉 AI「你是谁、你要按什么格式写」。这本来就在系统提示的位置上。

**支持的变量（1.1.0）**：

| 变量 | 替换成 |
|---|---|
| `{{date}}` | 今天日期，如 2026-11-18 |
| `{{time}}` | 当前时间，如 21:30 |
| `{{weekday}}` | 星期几 |
| `{{doc_title}}` | 当前文档标题 |

> **变更记录（1.1.0）**：`{{content}}`（选中的笔记内容）已移除。
> 原设计想要「选中日记 → 注入模板」，实际使用中主人改成「内容直接敲进输入框」，素材这一层就成了死重量：它带来一个空输入框、一个没人用的变量、和一堆状态管理代码。
> 移除后变量从 5 个减到 4 个。

**使用方式（1.1.0 的实际交互，与初版不同）**：

1. **主界面平铺一排提示词按钮** —— 点一下 = **只套用规则**，不清空对话、不自动发送
2. **右键菜单** —— 每模板一条，点了也是只套用规则并打开面板

> **为什么改**：初版设计是「点模板就生成」。实做后发现两个问题：
> ① 没取到素材时静默返回，按钮看起来是坏的；
> ② 主人的真实需求是「这个对话里每句话都按我的规则回答」，不是「一次性生成一篇文章」。
> 所以语义改成「绑定规则」：之后该对话的每条消息都带着它，点「新对话」也不取消。

**模板管理界面**：列表 + 新增 + 编辑 + 删除 + 排序。内置 3 个示例模板（日记复盘、内容扩展、要点总结），首次启动时写入，可随意删改。
入口在顶栏「管理」和提示词列表末尾的 `+`，从右侧抽屉打开。

**风险**：模板写得过长会撑爆上下文。发送前估算 token（粗略按字符数/2），超过模型上限时提示用户。

### 3.6 界面设计原则（1.1.0 新增）

界面重做的目标写在主人的原话里：**「更方便、更便捷、更高效地使用 MCP 和自定义提示词」**。

由此定了四条：

| 决定 | 理由 |
|---|---|
| 提示词**一直平铺**，不做下拉、不收起 | 所有模板一眼可见，少一次点击 |
| MCP **常驻一行状态条** | 主人的日记模板靠 MCP 取时间/天气，通没通必须一眼看见 |
| 模型与思考档位**放在主界面** | 两个高频开关，不该藏进设置 |
| 对话用**左右气泡** | 一眼分清谁说的，比「你 / AI」小标题直观 |

另外一条结构性决定：**设置/历史/模板/MCP 用右侧抽屉，不整页替换**。整页替换会把对话遮掉，改配置时没法对照。

### 3.7 主流 AI 对话能力

**必须有的**：

- 流式输出（打字机效果），可中途「停止」
- Markdown 渲染（标题、列表、表格、代码块高亮）
- 多轮上下文（可配置带最近 N 条）
- 「重新生成」上一条回答
- **「复制」按钮（核心出口）**：一键把当前这条回答的 Markdown 原文复制到剪贴板
- 会话列表（新建、切换、删除）

**复制功能的具体行为**：
- 每条 AI 回答右上角都有「复制」按钮
- 复制的是**原始 Markdown**，不是渲染后的富文本 —— 粘进思源后能正常识别标题、列表、加粗
- 点击后按钮变成「已复制」两秒，给个明确反馈
- 如果是通过右键菜单触发的生成，面板会自动打开并定位到这一条，方便直接复制

**不做**：插入到笔记 / 覆盖原文 / 图片上传 / 文件上传 / 语音 / 多模型并排 / 分享链接。

**为什么不做插入**：主人明确要求「不要牵扯到原本思源日记里面的东西」，自己复制更放心。这个决定顺带省掉了一整套「写块」API 和撤销机制。

## 四、技术上怎么搭

### 4.1 技术栈

| 项 | 选择 | 为什么 |
|---|---|---|
| 构建 | Vite 5 | 思源官方模板用的就是它，热更新快 |
| UI 框架 | Svelte 4 | 编译后体积小，无虚拟 DOM 开销，思源插件生态主流 |
| 语言 | TypeScript 5 | 类型检查能提前抓错，AI 参数结构复杂，强类型有必要 |
| 样式 | 原生 SCSS + 思源 CSS 变量 | 自动跟随思源主题（亮/暗），不引入 UI 组件库 |

**为什么不引入 UI 组件库**（如 Element、Ant Design）：体积大（几 MB），而且样式和思源原生风格打架。聊天面板的 UI 很简单，自己写更快更小。

**项目骨架**：以 `siyuan-note/plugin-sample-vite-svelte` 为起点（思源官方模板）。

### 4.3 网络请求怎么走（关键决策）

**主路径：直接 `fetch` + `ReadableStream`**

```ts
const resp = await fetch(url, { method: 'POST', headers, body, signal });
const reader = resp.body.getReader();
// 手动按行切分，处理 `data: {...}` 和 `data: [DONE]`
```

**为什么不用思源内核的 `/api/network/forwardProxy`**：
它**不支持流式** —— 必须等整个回答生成完才一次性返回。主人要打字机效果，这条路直接废掉。

**为什么直接 fetch 能行**：OpenAI 官方 API 和绝大多数中转站都返回 `Access-Control-Allow-Origin: *`。思源桌面端虽然是 Electron，但插件页面运行在 `http://127.0.0.1:6806` 这种本地地址上，跨域规则和普通浏览器一致。

**如果遇到不支持跨域的 API**：

1. 先试一次，失败给出明确中文提示：「这个接口不允许跨域访问，请换一个支持 CORS 的中转站」
2. 提供「兼容模式」开关：走 `/api/network/forwardProxy`，**但会失去流式**，界面要标清「此模式无打字机效果」

**收益**：99% 的情况能拿到完美的流式体验。
**风险**：极少数 API 用不了，已给出降级方案。

### 4.4 MCP 的 JSON-RPC 实现

自己写，不引第三方 SDK。

**为什么**：官方 `@modelcontextprotocol/sdk` 是给 Node 环境设计的，在浏览器里打包需要一堆 polyfill，而且它体积不小。MCP 的客户端协议本身很简单（JSON-RPC 2.0 over HTTP/SSE/stdio），核心就四个方法：`initialize`、`tools/list`、`tools/call`、`notifications/initialized`。自己写 200 行，可控、可调试、无依赖。

**stdio 传输在桌面端的实现要点**：

```ts
const req = (window as any).require;
if (typeof req !== 'function') throw new Error('当前环境不支持本地 MCP');
const { spawn } = req('child_process');
const child = spawn(command, args, { env: { ...process.env, ...extraEnv } });
// 按行读取 child.stdout，每行一个 JSON-RPC 消息
```

**风险**：如果思源某个版本封了 `window.require`，stdio 直接失效。所以：
- 启动时做能力检测，拿不到就隐藏 stdio 选项
- 界面上写清楚「本地 MCP 仅桌面版可用」

### 4.5 数据存哪里

全部用思源的插件存储 API：

```ts
await this.saveData('settings.json', settings);   // 设置
await this.saveData('sessions.json', sessions);   // 会话历史
```

实际落地在 `工作空间/data/storage/petal/<插件名>/` 下。

**为什么不用 localStorage**：思源的数据目录会跟着工作空间同步；localStorage 不会，换设备就丢。

**API Key 的安全**：明文存在本地文件里。思源本身是本地优先软件，这和工作空间里其他数据一个级别。**文档里要如实告诉主人这一点**，不要假装加密了。

## 八、我不想隐瞒的风险

1. **第三方中转站质量参差**：有的声称支持 `reasoning_effort` 实际忽略，有的流式返回格式不规范。第一版只保证官方 API 和规范实现可用。
2. **stdio MCP 是「灰色地带」**：依赖 Electron 的非公开能力，思源升级可能失效。
3. **没有自动化测试覆盖真实 API**：测试只能验证请求体构造和 SSE 解析逻辑，真实调用要主人自己配 key 试。
4. **上下文超限**：长日记 + 长模板 + 多轮历史可能超出模型窗口。第一版只做粗略估算 + 提示，不做自动截断。
5. **MCP 服务器要你自己找**：插件不提供现成的搜索服务。找到一个可靠的搜索类 MCP 服务器并配好 Key，这一步得你亲自弄，我会在设置页给图文指引。
